# CASE-002: Web Scanning Baseline, Detection Tuning and Canary Deployment

## Case Summary

| Field | Value |
|---|---|
| Case ID | CASE-002 |
| Monitoring Period | Approximately 48 hours |
| Data Source | Nginx access logs collected in Microsoft Sentinel |
| Initial Detections | UC001, UC002, UC004 |
| Detection Outcome | High volume of automated Internet scanning and reconnaissance |
| Engineering Outcome | Detection tuning and implementation of canary-based detections |
| New Detections | UC006, UC007, UC008 |
| Impact | Improved signal quality and higher-confidence reconnaissance detection |

## Background

After deploying the public web sensor and forwarding Nginx telemetry to Microsoft Sentinel, the environment was monitored for approximately 48 hours to establish an initial baseline of Internet-facing activity.

The monitoring period showed that publicly exposed web infrastructure receives continuous automated reconnaissance even without being actively advertised as a target.

Multiple external sources attempted to enumerate common administrative, configuration, backup and framework-specific resources.

## Initial Observation

The initial web analytics rules generated repeated alerts associated with automated scanning behavior.

The activity included:

- enumeration of common web paths,
- requests for administrative interfaces,
- probing for configuration and backup files,
- large numbers of unique paths requested within short time windows,
- repeated HTTP 404 responses,
- automated scanner-like request patterns.

The activity was detected primarily through:

- **UC001 - Web Scanner Detection**
- **UC002 - Sensitive File Discovery**
- **UC004 - High Request Rate**

The detections were working as designed, but the monitoring period demonstrated that the original thresholds were too sensitive for the normal background noise of an Internet-facing service.

## Detection Tuning

The alerts were reviewed to determine whether the observed activity represented targeted behavior or routine Internet-wide scanning.

Based on the observed telemetry, the following rules were tuned:

### UC001 - Web Scanner Detection

The threshold was increased to require both a higher number of requests and a higher number of unique requested paths within a one-minute window.

The objective was to reduce alerts generated by low-volume background scanning while preserving visibility into aggressive enumeration.

### UC002 - Sensitive File Discovery

The rule was adjusted to require a larger number of unique sensitive-resource requests within the detection window.

This retained visibility into broad sensitive-file enumeration while reducing noise from isolated probes.

### UC004 - High Request Rate

The detection was tuned to require both high request volume and sufficient path diversity.

This helped distinguish repetitive benign requests from broader automated reconnaissance.

The tuning decisions were based on observed traffic rather than arbitrary threshold selection.

## Detection Engineering Decision

The baseline review highlighted an important limitation of purely behavioral web-scanning detections.

Request volume and path diversity are useful for identifying scanners, but Internet-facing systems naturally receive significant background reconnaissance.

A second detection layer was therefore introduced using dedicated canary resources.

The objective was to create resources that have no legitimate operational purpose and should not be accessed by normal users or application workflows.

Interaction with these resources provides a much higher-confidence signal than generic scanning activity.

## Canary Detection Strategy

Three dedicated detections were introduced.

### UC006 - GitHub Canary Endpoint Access

A decoy resource in the public repository contains intentionally fake technical information referencing a dedicated canary endpoint.

The endpoint is not part of legitimate application functionality.

Access to it may indicate that the decoy content was discovered, reviewed and acted upon.

The specific endpoint is intentionally excluded from this public case study.

### UC007 - Blog Canary Endpoint Access

A separate hidden canary endpoint exists only within the web environment and is not referenced by legitimate website navigation or the public repository.

Access may indicate:

- automated endpoint discovery,
- directory enumeration,
- manual reconnaissance,
- targeted probing of hidden application resources.

The endpoint is intentionally not documented publicly.

### UC008 - Canary Asset Access

An additional decoy web resource provides a secondary reconnaissance signal.

This detection can be correlated with other web-scanning activity to strengthen investigation context.

The exact resource location is intentionally omitted.

## Alert Handling

Canary alerts include investigation context such as:

- source IP address,
- target host,
- HTTP method,
- requested resource,
- canary type,
- timestamp.

The source IP is mapped as a Microsoft Sentinel entity to support investigation and enrichment.

Repeated alerts from the same IP can be grouped into a single incident within a defined time window to reduce unnecessary incident duplication.

## Result

The monitoring exercise demonstrated three distinct levels of web activity:

1. routine Internet background scanning,
2. aggressive automated enumeration,
3. interaction with intentionally planted decoy resources.

The original behavioral detections continue to provide broad visibility into reconnaissance activity.

The tuned thresholds reduce unnecessary noise, while the new canary detections provide higher-confidence alerts that can be prioritized during investigation.

The result is a detection model that combines broad behavioral monitoring with focused deception-based signals.

## Lessons Learned

This exercise demonstrated that detection engineering is an iterative process.

Writing a query is only the first stage. Effective detections require:

- collecting real telemetry,
- establishing a baseline,
- validating detection assumptions,
- reviewing false-positive and low-value patterns,
- tuning thresholds,
- identifying detection gaps,
- introducing higher-confidence signals,
- continuously evaluating detection quality.

The exercise also showed that alert reduction should not simply mean disabling noisy detections.

Instead, low-value noise can be reduced while additional detection mechanisms are introduced to increase confidence and investigative value.

## Future Improvements

Planned improvements include:

- correlation between scanner detections and canary interaction,
- automated reputation enrichment for canary source IPs,
- temporary automated blocking for high-confidence canary interaction,
- additional decoy scenarios representing different reconnaissance techniques.

Automated blocking will only be introduced after safeguards and false-positive controls are validated.
